# CleanDesk 0.5.0-beta 多监控文件夹改造计划

## 1. 当前单目录架构摘要

当前稳定版本基于 `v0.4.0-beta`，核心仍是单监控文件夹模型。

### 启动与对象关系

- `main.py` 创建 `QApplication`、`CleanDeskService` 和 `MainWindow`。
- `CleanDeskService` 在初始化时读取 `ConfigStorage.load()`，创建：
  - `FileOrganizerEngine`
  - `FileProcessingWorker`
  - `FolderWatcher`
- `MainWindow` 只通过 service 层调用功能，不直接调用 engine。

### 当前配置结构

`storage.py` 当前默认配置为：

```json
{
  "monitored_folder": "...",
  "welcome_shown": false,
  "rules": []
}
```

`CleanDeskService.__init__()` 从 `config["monitored_folder"]` 读取单一路径到 `self.monitored_folder`。

`_persist_config()` 会写回：

- `config["monitored_folder"]`
- `config["rules"]`

### 当前扫描流程

- `scan_now()` 调用 `_ensure_folder_ready()` 检查单个 `self.monitored_folder`。
- `_queue_existing_files()` 遍历 `Path(self.monitored_folder).iterdir()` 的顶层文件。
- 每个文件进入 `FileProcessingWorker.enqueue(file_path, base_folder, rules, batch_id, mode, force=True)`。
- worker 调用 `engine.process_file_result(file_path, base_folder, rules, conflict_resolver)`。

### 当前监听流程

- `FolderWatcher.start(folder)` 每次只监听一个目录。
- 内部创建一个 `Observer`，对单个 path `schedule(CreatedFileHandler(...), recursive=False)`。
- watcher 只发出 `file_detected = Signal(str)`，没有携带来源根目录。
- service 中 `process_file(file_path)` 收到事件后，使用当前 `self.monitored_folder` 作为 `base_folder` 入队。

### 当前目标路径逻辑

`engine.py` 调用 `utils.resolve_target_folder(base, rule["target"])`：

- 目标是绝对路径：直接使用规范化绝对路径；
- 目标是相对路径：拼到当前源监控目录下；
- 该逻辑是多文件夹版本必须保留的关键点。

### 当前撤销与活动

- 撤销栈位于 `CleanDeskService.undo_stack`。
- batch 项目前只保存：
  - `filename`
  - `original_path`
  - `target_path`
- `_record_moved_file()` 将移动结果写入撤销 batch 和最近活动。
- `_display_path()` 目前默认相对 `self.monitored_folder` 展示路径。
- `is_undoing` 与 `ignore_until` 用于防止撤销移回文件被 watcher 立即再次整理。

## 2. 多目录目标架构

0.5.0-beta 的目标是引入多个监控文件夹，但保持规则全局、操作简单。

### 产品边界

- 支持添加、选择、删除多个监控文件夹。
- 不支持每个文件夹独立规则。
- 不支持每个文件夹单独 Start / Stop。
- Start 后扫描并监听所有已配置的有效文件夹。
- Stop 后停止所有监听。
- 运行中禁止添加、删除或修改监控文件夹。

### 推荐 service 内部模型

新增一个 service 层标准化列表：

```python
self.monitored_folders = [
    {
        "id": "...",
        "path": "...",
        "display_name": "下载"
    }
]
self.active_folder_id = "..."
```

同时保留兼容属性：

```python
self.monitored_folder
```

但它应变为“当前选中文件夹路径”的只读兼容入口，供 UI 渐进迁移。最终新代码应优先使用：

- `get_active_folder()`
- `get_active_folder_path()`
- `set_active_folder(folder_id)`
- `add_monitored_folder(path)`
- `remove_monitored_folder(folder_id)`

### 文件夹 ID

- 使用 `uuid4().hex`。
- ID 只作为 UI 选择和 watcher 事件关联，不参与路径判断。

### 路径标准化

建议在 service 层新增统一工具：

```python
normalize_folder_path(path) -> str
```

规则：

- `Path(path).expanduser().resolve()`；
- Windows 下用 `os.path.normcase(os.path.abspath(...))` 做比较 key；
- 保存到 config 的 `path` 使用规范化绝对路径字符串；
- 比较重复、父子嵌套时使用 normcase 后的绝对路径。

## 3. 配置迁移方案

迁移应放在 `storage.py`，原因：

- 配置兼容属于数据读取边界；
- service 不应关心旧 JSON 字段；
- 可以保证 service 拿到的数据始终是新结构。

### 新配置结构

建议结构：

```json
{
  "monitored_folders": [
    {
      "id": "唯一ID",
      "path": "D:\\Users\\...\\Downloads",
      "display_name": "下载"
    }
  ],
  "active_folder_id": "唯一ID",
  "welcome_shown": false,
  "rules": []
}
```

### 旧配置迁移

读取配置时：

1. 如果存在 `monitored_folders`：
   - 标准化列表；
   - 去掉空路径；
   - 修复缺失 id；
   - 修复缺失 display_name；
   - 校验 `active_folder_id` 是否存在。

2. 如果不存在 `monitored_folders`，但存在旧字段 `monitored_folder`：
   - 将旧路径迁移为列表第一项；
   - 自动生成 id；
   - `display_name` 使用路径末级目录名，例如 `Downloads`；如果为空则用“文件夹”；
   - `active_folder_id` 指向该项；
   - 保留 `rules`、`welcome_shown` 和其他已有字段。

3. 如果旧路径为空：
   - `monitored_folders` 使用空列表；
   - `active_folder_id` 为空；
   - UI 显示未添加文件夹。

### 保存策略

0.5 起保存新字段：

- `monitored_folders`
- `active_folder_id`
- `rules`
- `welcome_shown`

可暂时保留 `monitored_folder` 作为兼容字段，值等于当前选中文件夹路径；但后续版本可移除。这样可以降低 UI 和旧测试的迁移风险。

### 路径不存在处理

迁移时不自动创建目录，只保留配置。

运行时处理：

- 添加文件夹时要求路径存在且是目录；
- Start 时对不存在或无权限的目录跳过；
- 最近活动显示“某文件夹不可用，已跳过”；
- 其他有效目录继续扫描和监听。

### 重复和父子嵌套处理

在 `service.add_monitored_folder(path)` 中拒绝：

- 与已有路径完全相同；
- 新路径是已有路径的子目录；
- 新路径是已有路径的父目录。

比较方法：

- 所有路径使用 normalized absolute path；
- 用 `Path.relative_to()` 或 `os.path.commonpath()` 判断父子关系；
- Windows 下比较前使用 normcase。

## 4. watcher 改造方案

### 推荐方案：一个 Observer 管理多个 schedule

使用一个 `Observer` 管理多个目录的 schedule，优点：

- watchdog 支持一个 observer schedule 多个路径；
- Stop 只需停止一个 observer；
- 比每个文件夹一个 observer 更简单；
- 更容易保持现有 `FolderWatcher.stop()` 语义。

### watcher API 设计

将 `FolderWatcher.start(folder)` 改为：

```python
start(folders: list[dict])
```

每个 folder 包含：

- `id`
- `path`
- `display_name`

事件信号改为：

```python
file_detected = Signal(dict)
```

payload 示例：

```python
{
  "file_path": "...",
  "folder_id": "...",
  "source_root": "...",
  "display_name": "下载"
}
```

### 事件关联方式

为每个 schedule 创建独立 handler：

```python
CreatedFileHandler(watcher, folder_id, source_root, display_name)
```

handler 在 `on_created/on_moved` 中把上下文一起 emit。

### service 处理 watcher 事件

新增：

```python
process_file_event(event: dict)
```

逻辑：

1. 读取 `file_path`、`folder_id`、`source_root`；
2. 校验 folder_id 仍在当前配置中；
3. 使用 `source_root` 作为 engine 的 `base_folder`；
4. 入队时传入 `folder_id/source_root/display_name`；
5. 最近活动和撤销记录保留来源信息。

### worker 队列扩展

当前队列元素：

```python
(file_path, base_folder, rules, batch_id, mode)
```

建议扩展为 job dict，降低继续加字段的风险：

```python
{
  "file_path": "...",
  "base_folder": "...",
  "folder_id": "...",
  "folder_name": "...",
  "rules": [...],
  "batch_id": "...",
  "mode": "manual" | "auto"
}
```

这是 0.5 中风险较高但值得做的小重构。也可以阶段 A 暂时保持 tuple 并追加字段，但可读性较差。

### 重复处理风险与防护

1. 多个根目录重叠：
   - 添加阶段禁止父子嵌套；
   - 迁移时如果发现旧配置出现嵌套，保留第一项，后续项标记为无效或跳过并提示。

2. 目标子文件夹移动后重复处理：
   - 当前 watcher 是 `recursive=False`，相对目标目录在监控文件夹子目录内不会触发子目录内部文件事件；
   - 多目录下必须保持 `recursive=False`；
   - 如果绝对目标目录本身也是另一个监控根目录，应在添加文件夹时禁止这类嵌套或重复关系。

3. Start 初始扫描与 watcher 事件重复：
   - 当前 worker 有 `recent_paths` 防抖；
   - Start 时仍先 queue，再 start watcher 或维持现状但强制队列 `force=True`；
   - 多目录建议顺序：先创建聚合 batch，扫描所有有效目录入队，再启动 watcher；
   - watcher 事件到达后仍经过 worker dedupe。

4. 撤销文件被 watcher 再次整理：
   - 保留 `is_undoing`；
   - `ignore_until` key 继续用完整文件绝对路径；
   - 撤销冲突重命名时，必须 ignore 最终恢复路径；
   - 多目录下不需要按 folder_id 维护 ignore，因为路径本身足够唯一。

5. create / modify 重复事件：
   - 当前 watcher 只监听 created/moved；
   - worker `recent_paths` 继续防抖；
   - 多目录下 dedupe key 仍使用 normalized file path。

### 单个目录不可用

Start 时：

- 对每个 configured folder 独立检查；
- 不存在或无权限则跳过；
- 最近活动增加中文提示；
- logger 记录详细技术信息；
- 至少一个有效目录才进入 Running；
- 如果全部无效，保持 Stopped 并提示用户。

## 5. UI 改造方案

只做最小改动，将当前“监控文件夹”卡片升级为“监控文件夹列表”。

### 监控文件夹卡片

标题：

- `监控文件夹（2）`

副标题：

- 停止状态：`选择要整理的文件夹；开始后会监听所有文件夹。`
- 运行状态：`自动整理运行中。停止后可管理监控文件夹。`

列表项显示：

- 文件夹名称；
- 完整路径；
- 当前选中状态；
- 不显示绝对路径操作按钮以外的技术信息。

操作：

- `+ 添加文件夹`
- `移除当前文件夹`

运行中：

- 禁用添加、删除；
- 禁用文件夹选择切换是否需要谨慎：建议允许查看选择，但不允许修改列表；
- 明确提示“停止自动整理后可管理监控文件夹”。

### 当前文件夹语义

当前选中文件夹影响：

- `整理当前文件夹`；
- `智能整理建议`；
- 新建/编辑规则弹窗中的“选择...”默认目录；
- 智能建议弹窗目标目录选择默认位置。

### 按钮文案建议

- Start：建议改为 `开始自动整理`，更符合多目录语义；
- Stop：保持 `停止` 或改为 `停止自动整理`；
- Scan Now：建议改为 `整理当前文件夹`，避免误解为扫描所有文件夹；
- 智能整理建议：保持不变，但只分析当前选中文件夹。

### 状态卡

Stopped：

- `已停止`
- `添加或选择文件夹后，可整理当前文件夹。`

Running：

- `运行中`
- `正在监听 2 个文件夹`

如果部分目录失败：

- 状态仍为运行中；
- 最近活动提示具体跳过的目录。

### 最近活动来源目录

活动项 detail 增加来源：

```text
来自：下载
已移动到：安装包
命中规则：安装包
```

规则：

- 首页不显示完整绝对路径；
- 显示 `display_name`；
- 鼠标 tooltip 可选展示完整路径；
- 详细日志保留完整技术路径。

### 响应式布局

现有响应式由 `update_responsive_layout()` 控制：

- 宽屏双栏；
- 窄屏单栏；
- 外层 `QScrollArea`。

多目录列表只替换 folder_card 内部，不改变整体响应式结构。列表应：

- 禁止横向滚动；
- 路径文本自动换行或省略；
- 至少能显示 2-4 个文件夹；
- 窄屏时按钮可换行，不挤压路径。

## 6. 撤销、规则、智能建议兼容方案

### 规则

- 规则仍是全局列表；
- `rules.py` 的匹配顺序不变；
- `service.add_rule/update_rule/delete_rule/move_rule` 基本不需要改动业务语义；
- 相对 target 在 engine 中根据每个 job 的 `base_folder` 解析，因此天然支持多目录。

### 智能整理建议

`analyze_smart_suggestions()` 从：

```python
folder = Path(self.monitored_folder)
```

改为：

```python
folder = Path(self.get_active_folder_path())
```

只分析当前选中的文件夹顶层文件。

`添加规则并整理` 继续调用“整理当前文件夹”的扫描路径，不启动监听，不扫描其他文件夹。

### 撤销

撤销 batch item 建议扩展为：

```json
{
  "filename": "test.pdf",
  "original_path": "...",
  "target_path": "...",
  "folder_id": "...",
  "folder_name": "下载",
  "source_root": "..."
}
```

语义：

- 手动扫描当前文件夹：一个 batch；
- Start 前扫描所有文件夹：一个聚合 batch；
- watcher 自动整理单文件：单文件 batch；
- 撤销时仍按 target_path -> original_path 移动；
- `ignore_until` 记录最终恢复路径；
- 最近活动展示来源文件夹。

### 打开所在位置

活动中保留：

- `target_path`
- `target_folder`

无需改变核心实现。

### 目标路径解析

`utils.resolve_target_folder(monitored_folder, configured_target)` 保持不变。

多目录下关键是每个文件处理 job 必须传入正确的 `base_folder`，即文件所属监控根目录，而不是当前 UI 选中的文件夹。

## 8. 风险与回滚方式

### 风险 1：配置迁移导致用户监控目录丢失

缓解：

- 迁移放在 `storage.py`；
- 保留旧字段 `monitored_folder` 一个版本；
- 迁移前后都不删除旧数据；
- 对空路径和不存在路径保留配置但运行时提示。

回滚：

- 如果迁移出现问题，可以让 service 优先读取旧 `monitored_folder`；
- 由于不删除旧字段，回滚到 0.4 仍有机会继续使用单目录。

### 风险 2：多 watcher 事件来源归属错误

缓解：

- watcher handler 必须绑定 folder_id/source_root；
- worker job 必须携带 base_folder；
- engine 不根据当前 UI 状态推断 source root。

回滚：

- 保留单目录 watcher start 分支；
- 出问题时临时只监听 active folder，避免错误移动。

### 风险 3：相对目标路径落到错误目录

缓解：

- 不改 `resolve_target_folder()`；
- 每个 job 明确传入文件所属 source_root；
- 测试两个源目录同名文件的相对目标路径。

回滚：

- 如果多目录扫描出现异常，可暂停多目录 Start，只保留当前文件夹 Scan Now。

### 风险 4：撤销与监听冲突回归

缓解：

- 保留 `is_undoing`；
- `ignore_until` 使用最终恢复路径；
- 撤销 batch 增加 folder metadata；
- listener 事件仍统一经过 `_should_ignore_file_event()`。

回滚：

- 若撤销在多目录下不稳定，可暂时在撤销时阻止新增 watcher 入队，完成后恢复。

## 10. 受影响文件清单

预计 0.5 实施会影响：

- `storage.py`：配置迁移和新配置结构；
- `service.py`：多文件夹状态、扫描、监听入口、撤销与活动来源；
- `watcher.py`：多 schedule 和事件 payload；
- `ui.py`：监控文件夹列表、当前文件夹选择、运行中禁用管理、活动来源展示；
- `utils.py`：可能新增路径标准化/父子目录判断工具；
- `README.md`：多文件夹使用说明；
- `version.py`：版本号；
- `releases/0.5.0-beta/*`：发布归档。

尽量不改：

- `engine.py`：保留现有文件移动、冲突处理和目标路径解析调用方式；
- `rules.py`：保留全局规则、优先级和匹配逻辑。
